- Decision: Initialize EJS recording before active implementation orchestration.
  - Reason: Repository instructions require session recording from session start.
  - Impact: Traceable collaboration and decision history for this session.
- Decision: Pin explicit package versions for core runtime and tooling (`@babylonjs/core`, `@babylonjs/gui`, `cannon-es`, `typescript`, `vite`).
  - Reason: PRD Section 19 requires pinning/mitigating dependency risk.
  - Impact: Reproducible builds for all agents and CI.
- Decision: Use tree-shaking-friendly Babylon submodule imports in bootstrap entrypoint.
  - Reason: Supports bundle-size and modularity goals (NF-02 and Section 5.1 guidance).
  - Impact: Foundation remains lightweight and extension-ready for subsystem agents.
- Decision: Use a hidden placeholder mesh as the FollowCamera target in Phase 1.
  - Reason: Camera must run before gameplay entity systems exist, while still supporting heading-based follow behavior.
  - Impact: Gameplay systems can later replace or drive the target without refactoring camera setup.
- Decision: Keep asset loading in a typed placeholder module using local-path-only validation.
  - Reason: Phase 1 requires safe scaffolding without committing to full asset pipeline or remote dependencies.
  - Impact: UI/loading and gameplay systems can integrate progress and results via stable contracts in later phases.
- Decision: Use fixed-step simulation at 60 Hz for Phase 1 movement and containment updates.
  - Reason: Deterministic stepping keeps thrust/drag behavior stable across variable frame rates.
  - Impact: Player control feel and boundary collision remain predictable prior to full physics adoption.
- Decision: Implement arena collision fallback via bounds clamp and outward-velocity cancellation.
  - Reason: Phase 2 owns Cannon integration, but Phase 1 still requires containment and visible barriers.
  - Impact: The player remains inside the arena now without adding premature physics engine complexity.

# Key Learnings
Technical insights
- Babylon modular imports require precise module paths (e.g., `Color4` from `Maths/math.color`).
- Minimal bootstrap can safely run without gameplay systems while preserving strict typing contracts.
- `FollowCamera` API in current Babylon version expects `attachControl()` and a mesh target; `TransformNode` lock targets are not accepted by type contracts.
Prompting insights
- Phase-scoped delivery requests benefit from explicit verification runs (`build`, `test`) before handoff.
Tooling insights

- Under `verbatimModuleSyntax`, type-only imports must be explicit to avoid compile breaks during architecture refactors.
