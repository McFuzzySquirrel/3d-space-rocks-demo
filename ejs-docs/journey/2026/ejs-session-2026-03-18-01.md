  - Original materials are cloned and stored before flash to ensure clean restoration without material mutations.
  - Camera shake uses sine/cosine waves for smooth motion (not jittery); offsets applied on X/Y axes with intensity decay over time.
  - Shake intensity is 0.3 units per config, scaled by multiplier; typical duration is 0.1s per impact event.

- Decision: Run EJS session initialization at start of implementation.
  - Reason: Repository contract requires continuous journey capture.
  - Impact: Full traceability from kickoff through commit/wrap-up.
- Decision: Use latest stable toolchain/dependency versions for new bootstrap.
  - Reason: PRD requires current, stable tooling and pinned reproducibility.
  - Impact: Modern baseline with deterministic build behavior.
- Decision: Keep Phase 1 gameplay collision as non-physics bounds containment.
  - Reason: Cannon integration is a Phase 2 deliverable.
  - Impact: Phase 1 scope achieved without premature subsystem coupling.
- Decision: Adopt Engineering Journey System workflow (hooks + journey + ADR discipline) as standard process.
  - Reason: Workflow directly affects all future sessions and documentation quality.
  - Impact: New long-lived engineering process boundary; ADR required.
- Decision: Use procedural vertex noise for asteroid irregularity instead of texture-based variation.
  - Reason: Procedural approach is offline-capable, requires no external textures, and is deterministic per seed.
  - Impact: All asteroids can be generated purely from geometry/noise, improving offline playability and reducing bundle size.
- Decision: Cache StandardMaterial instances per scene for asteroids and projectiles.
  - Reason: All asteroids use the same material, as do all projectiles; material reuse is a Babylon.js best practice.
  - Impact: Reduced material object count and GPU memory footprint.
- Decision: Make Asteroid entity return child array on destruction rather than auto-inserting into scene.
  - Reason: Decouples entity lifecycle from scene/wave manager; enables testing and flexible spawning strategies.
  - Impact: WaveManager retains control over when and where child asteroids enter gameplay.
- Decision: Use Physics Impostor with Cannon.js body direct damping property access.
  - Reason: PhysicsImpostor API does not expose linear/angular damping in constructor; accessing underlying body is the prescribed pattern in Babylon.js/Cannon.js integration.
  - Impact: Arcade-feel movement with proper momentum decay can be achieved without relying on gravity-based drag.
- Decision: Refactor Player from function-based to class-based entity.
  - Reason: Consistency with Asteroid/Projectile class-based pattern enables cleaner state management, event emission, lifetime tracking, and input handling; backward-compatible factory preserves Game.ts interface.
  - Impact: Player lifecycle now integrated with event bus (playerEvents); firing and collision response encapsulated as typed methods; easier to test and extend.
- Decision: Projectile firing input (Spacebar) handled directly in Player keydown listener.
  - Reason: Immediate response without extra indirection; InputManager is a Phase 3+ enhancement; Player owns fire rate cooldown and projectile cap logic.
  - Impact: Input-to-firing latency minimized; fire rate difficulty tuning centralized in Player.PLAYER_COMBAT_CONFIG.
- Decision: Use countdown timer for invulnerability state instead of boolean flag.
  - Reason: Enables precise frame-accurate transitions and VFX synchronization; cleaner integration with update() loop.
  - Impact: VFX artist can query `player.isInvulnerable` during damaged$-emitted window; no need for separate event to clear invulnerability.
- Decision: Projectile cap at 10 active projectiles with early return on fire cooldown.
  - Reason: PRD Section 21 default assumption; prevents memory leaks from spam firing; encourages tactical/arcade-style play.
  - Impact: Fire rate becomes primary player limitation (10 projectiles × 0.1s cooldown = 1s mag dump); players must manage shots strategically.
- Decision: ScoreSystem tracks destroyed asteroids in Set<object> to prevent double-scoring on projectile+asteroid destruction event pairs.
  - Reason: When a projectile hits an asteroid, both entities emit destroy events; only one score event should be emitted per asteroid.
  - Impact: Asteroid instance is used as unique key; scoring is deterministic and single-threaded; no race conditions between event handlers.
- Decision: Use localStorage for high-score persistence with try/catch error handling.
  - Reason: localStorage may be unavailable in privacy-mode browsers or quota-exceeded scenarios; graceful degradation is safer than crashing.
  - Impact: High score persists across sessions in normal conditions; privacy-mode users still play but high score resets each session; no runtime errors or console spam.
- Decision: Implement ScoreSystem as centralized independent service, not delegated to WaveManager or Game.ts.
  - Reason: Scoring is cross-cutting concern from multiple sources (asteroids, waves, areas); dedicated service maintains single-responsibility and testability.
  - Impact: ScoreSystem is injectable/testable in isolation; Game.ts, WaveManager, and audio/VFX systems subscribe to scoreChanged$ independently; no tight coupling.
- Decision: Support score multiplier (default 1.0) for future difficulty scaling and power-ups.
  - Reason: PRD Section 8.6 implies wave/area difficulty scaling; multiplier enables tunable balance without constants churn.
  - Impact: setMultiplier() allows Game.ts to adjust difficulty midrun; power-ups can boost score temporarily.

# Key Learnings
Technical insights
- Babylon modular import correctness and TS `verbatimModuleSyntax` type-only imports are common integration pitfalls.
- FollowCamera setup is best isolated in a dedicated module with a replaceable target contract.
- Fixed-step updates keep movement behavior stable prior to full physics.
- Procedural vertex displacement via multi-octave noise is effective for creating organic irregular shapes without external textures.
- StandardMaterial property names in Babylon v8: use `diffuseColor` (not `diffuse`), import from `@babylonjs/core/Materials/standardMaterial` for type safety.
- After vertex deformation, calling `createNormals(true)` is essential for correct lighting after displacement.
Prompting insights
- Specialist delegation is effective when prompts contain strict phase boundaries and explicit out-of-scope constraints.
- Iteration quality improves when each delegation includes validation requirements.
Tooling insights
- `python3 scripts/adr-db.py sync` should run at session boundaries.
- EJS hooks can warn on missing journey artifacts without blocking delivery unless explicitly enforced.

# If Repeating This Work
Do this:
- Initialize EJS, then run a tech-currency check before Phase 1.
- Delegate by phase with clear ownership and explicit validation gates.
- Commit at logical milestones to preserve recoverable state.
Avoid this:
- Mixing Phase 2 physics into Phase 1 implementation.
- Deferring journey updates until the end.
Watch out for:
- Babylon import/API drift across major versions.
- Hidden type regressions from non-type-only imports under strict TS settings.
