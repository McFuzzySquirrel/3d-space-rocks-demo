# Decisions Made
- Decision: Begin Phase 5 immediately after Phase 4 completion.
  - Reason: Human requested direct phase execution.
  - Impact: Offline support and installability will complete the PRD implementation sequence.
- Decision: Use build-injected versioned precache data in `sw.js` rather than a manually maintained asset list.
  - Reason: Vite emits hashed asset names, so hand-maintained lists would drift and break offline caching after changes.
  - Impact: Service worker remains deterministic while tracking real build outputs.
- Decision: Restrict service worker fetch handling to same-origin GET requests only.
  - Reason: PRD SP-04/SP-05 require own-origin-only caching and no runtime external dependencies.
  - Impact: Offline runtime stays inside the intended security boundary.
- Decision: Add a bundle-budget script instead of a larger automated browser test harness.
  - Reason: Phase 5 needed one executable release gate with low setup cost; bundle size is directly measurable and mapped to NF-02.
  - Impact: Release readiness now has a simple CI-friendly check without introducing brittle browser mocks.

# Key Learnings
Technical insights:
- Vite build hooks are sufficient to inject hashed asset lists and explicit version strings into a plain service worker without pulling in a heavier PWA plugin.
- Manual chunking improves cache granularity, but Babylon core still dominates the payload; deeper reductions would require import trimming or dynamic loading rather than more bundler tuning alone.
- A simple bundle-size gate is a practical automated release check for static browser games when full browser automation is not yet in place.

Prompting insights:
- Giving the QA agent the prior PWA implementation summary produced cleaner follow-on artifacts and avoided duplicate offline docs.
- Explicitly stating "no EJS/report files" continues to prevent the stray-file issue seen in earlier phases.

Tooling insights:
- `npm run check:bundle` is fast enough to run as part of every release verification pass alongside `npm run build`.
- `git diff --stat HEAD` plus `ls ejs-docs/journey/2026/` remains a good final verification pair before committing phase work.

# If Repeating This Work
Do this:
- Implement the service worker with build-time precache injection tied to real emitted assets.
- Add one automated release gate with clear PRD mapping, such as bundle size.
- Keep offline validation docs split into an implementation-specific plan and a QA-facing matrix/checklist.

Avoid this:
- Manually hardcoding hashed build asset names into the service worker.
- Catch-all fetch interception for cross-origin requests.
- Overbuilding browser automation before the repo has a stable test harness.

Watch out for:
- Large Babylon chunks still trigger Vite warnings even when the overall bundle budget passes.
- Secure-context requirements for service worker registration can make local validation appear broken if tested from the wrong origin.

# Future Agent Guidance
Prefer:
- Plain browser APIs and Vite hooks for PWA/runtime integration when the app is already static and simple.
- Same-origin-only cache logic with explicit cache prefixes and cleanup.
- Small executable release checks that map directly to PRD NFRs.

Avoid:
- External runtime assets or CDN dependencies in PWA/offline work.
- Mixing gameplay changes into release/distribution phases.
- Introducing broad test scaffolding during a release-hardening phase unless the repo already supports it.
