# Decisions Made
- Decision: Resolve player-to-asteroid impacts explicitly in `Game` update loop instead of relying on implicit physics side effects.
  - Reason: Ship destruction was not consistently triggered by asteroid collisions during gameplay.
  - Impact: Direct overlaps now deterministically apply player damage and destroy the impacting asteroid.
- Decision: Restore front wall alpha to `config.wallAlpha` when closing exit zone.
  - Reason: A hardcoded default alpha caused one wall to look different from the rest after transitions.
  - Impact: Barrier transparency remains visually consistent across all walls.
- Decision: Begin Phase 5 immediately after Phase 4 completion.
  - Reason: Human requested direct phase execution.
  - Impact: Offline support and installability will complete the PRD implementation sequence.
- Decision: Use build-injected versioned precache data in `sw.js` rather than a manually maintained asset list.
  - Reason: Vite emits hashed asset names, so hand-maintained lists would drift and break offline caching after changes.
  - Impact: Service worker remains deterministic while tracking real build outputs.
- Decision: Restrict service worker fetch handling to same-origin GET requests only.
  - Reason: PRD SP-04/SP-05 require own-origin-only caching and no runtime external dependencies.
  - Impact: Offline runtime stays inside the intended security boundary.
- Decision: Add a bundle-budget script instead of a larger automated browser test harness.
  - Reason: Phase 5 needed one executable release gate with low setup cost; bundle size is directly measurable and mapped to NF-02.
  - Impact: Release readiness now has a simple CI-friendly check without introducing brittle browser mocks.

# Key Learnings
Technical insights:
- Vite build hooks are sufficient to inject hashed asset lists and explicit version strings into a plain service worker without pulling in a heavier PWA plugin.
- Manual chunking improves cache granularity, but Babylon core still dominates the payload; deeper reductions would require import trimming or dynamic loading rather than more bundler tuning alone.
- A simple bundle-size gate is a practical automated release check for static browser games when full browser automation is not yet in place.

Prompting insights:
- Giving the QA agent the prior PWA implementation summary produced cleaner follow-on artifacts and avoided duplicate offline docs.
- Explicitly stating "no EJS/report files" continues to prevent the stray-file issue seen in earlier phases.

Tooling insights:
- `npm run check:bundle` is fast enough to run as part of every release verification pass alongside `npm run build`.
- `git diff --stat HEAD` plus `ls ejs-docs/journey/2026/` remains a good final verification pair before committing phase work.

# If Repeating This Work
Do this:
- Implement the service worker with build-time precache injection tied to real emitted assets.
- Add one automated release gate with clear PRD mapping, such as bundle size.
- Keep offline validation docs split into an implementation-specific plan and a QA-facing matrix/checklist.

Avoid this:
- Manually hardcoding hashed build asset names into the service worker.
- Catch-all fetch interception for cross-origin requests.
- Overbuilding browser automation before the repo has a stable test harness.

Watch out for:
- Large Babylon chunks still trigger Vite warnings even when the overall bundle budget passes.
- Secure-context requirements for service worker registration can make local validation appear broken if tested from the wrong origin.

# Future Agent Guidance
Prefer:
- Plain browser APIs and Vite hooks for PWA/runtime integration when the app is already static and simple.
- Same-origin-only cache logic with explicit cache prefixes and cleanup.
- Small executable release checks that map directly to PRD NFRs.

Avoid:
- External runtime assets or CDN dependencies in PWA/offline work.
- Mixing gameplay changes into release/distribution phases.
- Introducing broad test scaffolding during a release-hardening phase unless the repo already supports it.

### DECISIONS_EXTRACT
- Build-injected versioned precache in sw.js: Vite emits hashed asset names; static lists would drift after every build. Build hook injects real filenames + version hash into sw.js placeholders. (Hard-to-reverse once SWs are deployed to users — warrants ADR 0003.)
- Same-origin GET only for fetch interception: Enforces PRD SP-04/SP-05 own-origin security requirement; external requests fall through unmodified; prevents accidental offline failure from CDN dependency.
- Production-only SW registration: Guards in registerServiceWorker.ts (IS_PRODUCTION + serviceWorker in navigator + secure context) prevent dev-mode cache-stale issues entirely.
- Manual Babylon chunking in vite.config.ts: babylon-core, babylon-gui, babylon-render, physics → separate browser-cache entries; improves cache granularity on incremental deploys.
- Bundle-budget script over browser test harness: Executable npm script mapping directly to NF-02 chosen over full Vitest/browser automation; CI-friendly, zero mock setup, measurable PRD compliance.

### LEARNING_EXTRACT
Technical:
  - Vite build hooks are sufficient for deterministic precache injection without Workbox or vite-plugin-pwa; own-implementation keeps the dep footprint minimal.
  - Manual chunking improves browser cache utilization per-module; further payload reduction requires tree-shaking or dynamic import splitting, not more bundler config.
  - A single file-walking bundle-size script is a practical CI gate for static PWAs lacking a browser automation harness.
Prompting:
  - Providing the QA sub-agent a complete summary of the prior agent's deliverables reduces duplicated file discovery and produces cleaner handoff artifacts.
  - Explicit "no EJS/report files" in delegation prompts continues to prevent the stray-file issue; this pattern should be made a standing delegation contract.
Tooling:
  - npm run check:bundle is fast enough to run in every release pass alongside npm run build.
  - git diff --stat HEAD + ls ejs-docs/journey/YYYY/ remains a reliable final check before committing phase work.

### AGENT_GUIDANCE_EXTRACT
Prefer:
  - Vite build plugins for runtime injection into static assets (cache manifests, version strings); avoids stale-manifest risk from manual curation.
  - Same-origin-only service worker strategies for games and demos without external API dependencies.
  - Small, executable release gates with direct PRD NFR mapping (bundle budget, offline smoke test) over broad browser automation for early-stage repos.
Avoid:
  - Static/hardcoded hashed asset lists in service worker templates; they diverge from real build output immediately.
  - Cross-origin fetch interception or cache-warming of CDN dependencies in a privacy/security-conscious PWA.
  - Introducing full browser automation scaffolding during a release-hardening phase unless a stable test harness already exists.
  - Mixing gameplay changes into a distribution/offline phase.
