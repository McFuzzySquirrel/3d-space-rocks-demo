# Key Learnings
Technical insights
- ADR 0002 and ADR 0003 provide the most important architectural spine for the story because they represent durable system choices rather than implementation detail.
- Narrative docs are strongest when anchored to concrete artifacts (journeys, ADRs, commits, validations) rather than paraphrased sentiment.

Prompting insights
- Requests for a "story" still benefit from technical structure; the best output here came from extracting patterns first, then writing with energy second.
- Users often want documentation that is emotionally readable without losing engineering truth. That requires synthesis, not just summarization.

Tooling insights
- Reading the journeys and ADRs in parallel is efficient enough to recover the project arc quickly.
- EJS artifacts are useful not only for auditability but also as source material for user-facing retrospective content.

# If Repeating This Work
Do this:
- Read every relevant journey and ADR before writing the narrative, then identify the recurring roles, conflicts, and turning points.
- Write for an intelligent future reader who wants both story and operational lessons.
- Link the output from a visible index like the README.

Avoid this:
- Dumping raw session summaries into a document and calling it a story.
- Focusing only on features shipped while ignoring the process decisions that made the work scalable.

Watch out for:
- Incomplete journey files can skew the story toward the most polished sessions; compensate by using ADRs and completed sessions to identify the larger pattern.

# Future Agent Guidance
Prefer:
- Standalone retrospective docs for user-facing storytelling.
- Phase-based storytelling with ADR-backed turning points.
- Linking narrative docs from README or other visible entrypoints.

Avoid:
- Hiding useful narrative context inside EJS-only files when the audience is future users.
