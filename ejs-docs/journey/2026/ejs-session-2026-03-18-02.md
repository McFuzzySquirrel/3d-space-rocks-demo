# Decisions Made
- Decision: Begin Phase 3 immediately after Phase 2 commit.
  - Reason: Human requested continuous execution.
  - Impact: Wave/area progression and UI becomes available in same session.
- Decision: Move wave transition delay ownership to `Game.ts` state machine handlers.
  - Reason: Section 14 requires state-driven transitions (`PLAYING -> WAVE_TRANSITION -> PLAYING`) with deterministic guards.
  - Impact: Single transition authority, easier HUD synchronization via `gameStateEvents`.
- Decision: Extend `PlayerController` and `ArenaController` APIs rather than embedding transition side effects in unrelated systems.
  - Reason: Keeps gameplay coordination in `Game.ts` while exposing narrow typed hooks (input enable, reset, exit zone/barrier controls).
  - Impact: Reduced coupling and cleaner integration points for pause/area-complete behavior.
- Decision: Preserve player lives across area transitions while resetting position and motion.
  - Reason: PRD P-07 defines default lives on game start; transitioning areas should not implicitly heal the player.
  - Impact: Area progression keeps run continuity and challenge curve intact.
- Decision: Add player damage event subscription to HUD for lives display updates.
  - Reason: Lives are not emitted from score/wave state events, and HUD must keep life indicators + text synchronized in real time.
  - Impact: HUD life icons and accessible lives count remain correct without direct Player polling.

# Key Learnings
Technical insights:
- Babylon.js `Animation` API requires per-mesh material instances when animating properties independently across multiple sibling meshes — shared materials cause unintended side effects.
- In RxJS-driven state machines, timer ownership must live in one authoritative place. Splitting timing between WaveManager and Game.ts creates subtle ordering races that are difficult to debug.
- Returning a `ParticleSystem` handle from a VFX function (vs. void) is the correct pattern when the caller needs lifecycle control (e.g., stopping a looping beacon on an event).
- `@babylonjs/gui` fullscreen ADT works well for layered overlays — a single ADT with `isVisible` toggling per-panel is more performant than creating/disposing multiple ADTs per state change.

Prompting insights:
- Sub-agents consistently created spurious EJS session files (-03, -04) when not explicitly instructed otherwise. Adding "Do NOT create EJS session files or summary markdown files" to delegation prompts is required.
- Providing the exact active session file path in the delegation prompt reduces sub-agent EJS blind spot.

Tooling insights:
- `python3 scripts/adr-db.py sync` must be run after any spurious file deletion to keep the indexed journey count accurate.
- `git diff --stat HEAD` before commit is a reliable way to verify the full Phase 3 change surface before committing.

Avoid this:
- Shared Babylon materials across meshes that MIGHT need independent animation later.
- Embedding transition side effects (input lock, player reset) in entity-level modules — keep them in `Game.ts` state entry handlers.
- Post-process pipelines for short-lived (< 0.5s) screen flash effects.

Watch out for:
- Sub-agents re-creating spurious journey session files (e.g., `-03.md`, `-04.md`) even after they were deleted — check `ls ejs-docs/journey/YYYY/` after each sub-agent call.
- `@babylonjs/gui` fullscreen texture disposal order — always dispose ADT before scene disposal to avoid dangling references.

# Future Agent Guidance
Prefer:
- Inversion-of-control via spawn/callback injection over direct imports between coordinating modules.
- Passive, event-driven HUD subscriptions over polling or direct-method coupling from `Game.ts`.
- Single-authority state coordination: all game phase transitions live in `Game.ts` setState() handler.
- Named observable streams (`waveManagerEvents.*`, `gameStateEvents.*`) for cross-module communication.

Avoid:
- Physics triggers for simple zone-proximity checks — use per-frame position comparison in the update loop.
- Embedding gameplay logic in HUD/UI classes — HUD must remain a passive subscriber.
- Multiple ADTs — one fullscreen ADT with panel visibility toggling is always preferable.
